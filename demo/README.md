# CLUE Demo App

This folder contains the Streamlit demo application used in the VLDB demo.

## The metric

CLUE explains **90-Day Customer Value**: the average value generated per acquired user during
their first 90 days after acquisition. It is observed history, not a prediction.

```text
90-Day Customer Value
  = 90-Day Purchase Conversion Rate    (Purchasing Customers / Acquired Users)
  x Orders per Purchasing Customer     (Total Orders / Purchasing Customers)
  x Average Order Value                (Total Gross Order Value / Total Orders)
```

Two time windows are involved and are never merged: the *reference acquisition period* decides
which cohort months are in view, and the *90-day observation window* runs from each user's own
acquisition date. Day 0 is the acquisition day, so the window is day offsets 0–89.

## Which cohort CLUE explains

CLUE explains **one acquisition month**: the most recent month in the reference period, which is
the same month the baseline dashboard's KPI cards report. Both apps apply that rule, so they
cannot disagree about which number is the headline.

The period arrives on the handoff link (`?start=YYYY-MM&end=YYYY-MM`), so a participant who
changed the dashboard's filter before clicking through sees the cohort they were actually looking
at. A missing or malformed parameter falls back to the dashboard's own default (Jan–Jun 2024)
rather than erroring — the link is generated by another app, and a study session should not die
on a bad URL.

## Quick Start

Run from this directory:

- `python -m pip install streamlit`
- `streamlit run main.py`

Numbers come from the modeled data source the baseline dashboard builds
(`baseline_dashboard/data/modeled/`). Without it, CLUE falls back to the spec's reference example
and says so in the overview card.

## File Guide

### data/metrics.py
Single source of every number CLUE displays.

What it does:
- Resolves the reference acquisition period from the handoff link, and pins the 90-day
  observation window.
- Computes the four base counts and the three factors from the modeled tables.
- Runs the consistency checks the main view surfaces as a banner.
- Falls back to the reference example when the data source is missing.

Main helpers:
- `compute_baseline()` / `load_baseline()` (cached)
- `run_checks(baseline)` / `failed_checks(baseline)`
- `node_values(baseline)` — formatted value per provenance node id
- `money()`, `percent()`, `count()`, `decimal()`

### data/graph_data.py
Provenance node/edge model, transformation flows, and simulation deltas.

What it does:
- Defines the provenance graph (`NODES`, `EDGES`, `LEAF_IDS`) with clipped-stem node ids:
  `cust_val`, `conv_rate`, `orders_per_cust`, `avg_order_val`, `acq_users`, `purch_cust_1/_2`,
  `tot_orders_1/_2`, `tot_gross_val`.
- Builds one transformation flow per leaf; four of them share `_acquisition_stage()`, the
  acquisition-group pipeline through to qualifying orders.
- Splits the wording by element: a node's `description` says what that table or column *is*,
  an edge's `label` names the kind of operation ("Filter applied", "Join") and its
  `description` carries the predicate, shown when hovering the operation chip.
- `simulation_deltas()` propagates an illustrative scenario from the historical baseline
  without modifying it.

### main.py
Entry point for the app.

What it does:
- Configures Streamlit page layout.
- Injects global primary-button style.
- Injects shared app styles from `components/styles.py`.
- Initializes global session state (`active_view`).
- Routes to either:
  - `render_main_view()`
  - `render_simulator_view()`

Main functions:
- `_inject_primary_button_style()`
- `_initialize_session_state()`
- `_render_active_view()`
- `main()`

### components/top_view.py
Shared top bar used by both views.

What it does:
- Renders app title (`CLUE`) and the metric being explained (`PRIMARY_METRIC`).
- Renders navigation button that switches `active_view`.

There is no metric selector: participants arrive from the baseline dashboard with the metric
already chosen, and CLUE explains one metric. The dashboard's `?metric=` parameter is accepted
and ignored, so no link lands on an empty page.

Main function:
- `render_top_view(button_text, view_type)`

### components/main_view.py
Main dashboard (non-simulator) view.

What it does:
- Shows overview card, explanation card, provenance card, and transformation card.
- Shows content when the selected metric is `PRIMARY_METRIC` (90-Day Customer Value).
- The explanation says what the metric *means*, not what it currently is. The figures are already
  on the overview card, in the provenance graph, and on the dashboard this hands over from —
  repeating them made the panel long enough that the explanation got lost, and gave three places
  for the same number to disagree.
- Renders the acquisition-month chart with Vega-Lite: one column per month in the reference
  period, with the explained cohort in the accent colour and every other month muted. This is
  the same chart the participant just left on the dashboard, so they arrive looking at the shape
  they clicked from.
- Surfaces failed consistency checks as an error banner.

Main helpers:
- `_is_customer_value_selected()`
- `_build_chart_values()`
- `_build_chart_vega_spec()`
- `_render_metric_overview()`
- `_render_ai_explanation()`
- `_render_provenance_view()`
- `_render_transformation_view()`
- `_report_checks()`
- `render_main_view()`

### components/simulator_view.py
Simulator workflow view.

What it does:
- Puts the goal, the three assumptions and the scenario readout across the first row, so every
  control is visible without scrolling; Scenario Starters and results run full width below.
- Shows the historical baseline and a planning goal (how much more value users acquired over
  the next 3 months should generate in their first 90 days).
- Renders the three assumptions as free-moving sliders — conversion rate, orders per purchasing
  customer, average order value — seeded at their observed values. They do not rebalance each
  other; the scenario is free to land above or below the goal.
- Lays the assumptions out in one row — the planning goal plus the three sliders, four columns of
  roughly equal height — and puts the live scenario in a band directly beneath, inside the same
  card and divided from it by a rule: headline on the left, the four implied figures side by
  side, the goal chip and Pin button on the right. One block with two halves, because the band is
  what those sliders produce. It is not repeated in the list.

  The band used to be a fifth column beside the sliders. Its content is a headline plus four
  figures, which stacked in a narrow column ran about 265px — that set the height of the whole
  row, and the three sliders, needing about 110px each, sat in a quarter-screen of nothing. Laid
  out wide it is a third of the height, and the row now reads as inputs then outcome instead of
  interleaving the two.
- Below that, one row holding two columns: the scenario list on the left, the simulation results
  on the right. The list holds an optional "Best observed" starting point plus any scenarios the
  participant has pinned — six slots in total, compact rows, scrolling vertically. Clicking a row
  selects it; the ✕ in its corner removes it.
- Results follow the selection immediately. There is no Simulate button: choosing a scenario and
  reading what it implies is a glance sideways, so the button, the started/not-started state and
  the scroll-into-view script all stopped being needed.
- With nothing selected the results panel says so. There is nothing to propagate until a scenario
  is chosen, and the sliders' own numbers are already on screen above.
- Renders the results as scenario assumptions → computed consequences → scenario result,
  followed by the propagation graph.

Main helpers:
- `_initialize_simulator_state()`
- `_render_step_slider()` — the planning goal
- `_render_controls_row()`, `_render_scenario_readout()`
- `_render_controls_row()`, `_render_scenario_strip()`, `_render_comparison_and_results()`,
  `_render_scenario_list()`, `_render_results_column()`, `comparison_cards()`
- `_assumption_lines()`, `_consequence_lines()`, `_result_lines()`
- `_render_simulation_output_panel()`
- `render_simulator_view()`

### data/scenario.py
Hypothetical scenario state, kept apart from observed history.

What it does:
- `Scenario` holds the three assumptions; purchasing customers, orders, gross value and the
  headline are propagated from them, so the spec's identities hold by construction.
- `from_baseline()`, `from_observed_best()`, `goal_value()`, `run_scenario_checks()`.

**Assumptions are taken exactly as set.** No tolerance band is applied anywhere. A band would be
*our* guess at what counts as a plausible movement, and the simulator exists precisely to let
someone explore a movement we have not anticipated — a campaign that beats anything in the
history, for instance. The sliders show the observed range for each factor underneath as
context, and are not capped by it.

**Nothing is generated on the participant's behalf.** An earlier version produced three
"starters" by solving backwards from the goal (`factor = goal ÷ current`), which meant that once
a participant's own assumptions passed the goal, every suggestion became a *cut* — it could tell
someone who had just raised conversion to 41% to set it to 36%. The goal is a **floor**;
exceeding it is success, and nothing pulls a scenario back to it.

**Scenarios are propagated on the future cohort**, `future_acquired_users` — the same three
months a year earlier, since acquisition is seasonal. Both sides of every "→" use it, so a card
never puts a 31-user group beside a 448-user one. It does not affect the headline at all
(customer value is per acquired user, so it divides out); it scales the absolute counts, which is
what makes the counts comparable across cards.
- Never writes to `BaselineMetrics` — changing an assumption cannot disturb the numbers the
  main view shows.

### utils/slider_calculations.py
Session-state plumbing for the scenario controls: `initialize_scenario_state()`,
`current_scenario()`, `load_scenario()`, `slider_bounds()`, `uplift_percent()`.

### components/styles.py
Global style system and small HTML helpers.

What it does:
- Builds and injects app-wide CSS (backgrounds, cards, sliders, typography, button tweaks).
- Provides helper for rendering bullet details in custom HTML boxes.

Main helpers:
- `_build_app_css()`
- `inject_checkbox_styles()`
- `inject_app_styles()`
- `_bullets_to_html_list(content)`
- `get_detail_box_html(content)`
- `get_selected_text_style()`
- `get_checkbox_label_html(label, is_selected=False)`

## Session State Keys

Common keys used in the app:
- `active_view`: `main` or `simulator`
- `selected_node`: provenance leaf whose transformation flow is shown
- `simulation_started`: controls output panel behavior
- `sim_uplift`, `sim_uplift_input`: planning goal, as a % above the historical baseline
- `sim_conversion`, `sim_orders_per_cust`, `sim_order_value`: the three scenario assumptions
- `sim_pinned_scenarios`: pinned pathway cards, as (name, Scenario) snapshots
- `sim_selected_scenario`: which card the simulation runs on
- `show_reference_card`: whether the "Best observed" starting-point card is shown

## Where To Edit What

- Change navigation behavior: `main.py`, `components/top_view.py`
- Change main dashboard cards/chart/text: `components/main_view.py`
- Change the metric definition, reference period, or checks: `data/metrics.py`
- Change provenance nodes or transformation flows: `data/graph_data.py`
- Change scenario propagation or Scenario Starters: `data/scenario.py`
- Change simulator controls or simulation flow: `components/simulator_view.py`
- Change visual style/theme/spacing: `components/styles.py`

## Tests

Run from this directory:

```
python -m unittest discover -s tests -t . -q
```

`tests/test_metrics.py` covers the metric layer, the checks, the handoff link contract, and —
importantly — asserts CLUE and the baseline dashboard produce identical figures for the same
period. `tests/test_graph_and_scenario.py` covers the provenance graph, the transformation flows
(including that they describe a *day*-based window, since prose does not fail loudly when the
definition underneath it changes), and scenario propagation.

Both suites skip rather than fail when the modeled data source has not been built.

## Two implementation notes on the comparison rail

**Rows carry real buttons, overlaid by CSS.** Each row is a container holding its HTML plus two
buttons that CSS lifts on top: one covering the whole row (clicking anywhere selects it) and a
small one in the corner (removes it). HTML alone cannot carry a Streamlit click. Those rules use
descendant selectors, not `div.stButton > button`: Streamlit wraps a button carrying `help` in a
tooltip target, so the button is a grandchild and a child selector silently matches nothing.

**Rows, not cards, because six have to fit.** A row carries only what tells scenarios apart —
name, headline, and the three assumptions. The implied pathway moved to the results panel, which
is where the reader is looking once a row is selected. The column keeps the width a card had on
the old horizontal rail; the rows got shorter, not narrower.

**The propagation graph is keyed by scenario.** `streamlit_flow` was called with a fixed key while
its state changed, which leaves the previously mounted graph on screen. That went unnoticed while
simulating was a button press and would be the first thing anyone saw now that selecting a row is
the whole interaction. The key carries a signature of the node deltas, and the cached flow states
are capped at six so a session does not accumulate one per slider step.

**Rail actions are `on_click` callbacks, not post-render branches.** Streamlit runs callbacks
before the script body, so the rail is drawn from state that already reflects the click.
Mutating state after drawing and calling `st.rerun()` instead left the removed card's keyed
container behind as a ghost — the card stayed on screen while the state said it was gone.
